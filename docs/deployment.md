# Deployment

The service runs as one container: a FastAPI web process with the job worker embedded. It needs a
PostgreSQL database for metadata and an S3-compatible bucket for every recording and artifact.
Nothing permanent is kept on the container's disk. The repository provides:

| File | Purpose |
|---|---|
| `Dockerfile` | Runtime image: Python 3.12, dependencies installed from `uv.lock` without dev or GPL test packages, non-root user |
| `scripts/docker-entrypoint.sh` | Starts one uvicorn process on `$PORT`; records the deployed commit for provenance |
| `render.yaml` | Render Blueprint: the web service, its PostgreSQL database, limits, and which secrets to prompt for |
| `.env.example` | Every setting with its default; copy to `.env` for a local server |
| `.github/workflows/ci.yml` | Runs the full gate, linting, and security scans on every push and pull request |
| `scripts/smoke.py` | Startup smoke test for a local server, a Docker image, or a deployed URL |

Status: no deployment has been made from this repository. The CI workflow runs on GitHub, where
the Docker image has been built and has passed its smoke test. The development machine has no
Docker, so local gate runs report AC-S9-09 as BLOCKED. What has been tested is listed at the end.

## Render (the planned topology)

`render.yaml` declares:
- one web service, plan `1c-2g` (1 CPU, 2 GB), Docker runtime, region Frankfurt, with:
  - health check `/readyz` (database and object store reachable);
  - pre-deploy command `python -m hvsr_web.admin migrate`;
  - auto-deploy only after CI checks pass;
- one PostgreSQL 16 database, plan `0.1c-256mb`, 1 GB disk with autoscaling, reachable only from
  Render's private network (`ipAllowList: []`).

The limits in the blueprint keep the measured peak memory of one web process plus one job process
under 95% of the instance's 2 GB (`docs/quotas-and-limits.md`, "Hosted values"). The free plans are
not used: a free web service loses its files when it spins down, and a free database expires after
30 days.

### 1. Create the bucket

Cloudflare R2 is the default; Backblaze B2 and Hetzner Object Storage are compared in
`docs/costs.md`. For R2:
1. Create a bucket (for example `hvsr-analyzer`). Keep it private: downloads use short-lived
   presigned URLs.
2. Create an R2 API token with Object Read & Write permission for that bucket only. Note the
   access key ID, the secret access key, and the account's S3 endpoint
   `https://<ACCOUNT_ID>.r2.cloudflarestorage.com`.

The adapter writes with `If-None-Match: *` (never overwrite a committed object) and a SHA-256
checksum. It was tested against moto (an S3 emulator) only, not against R2, B2, or Hetzner. Check
the first submission after deploying (step 5).

### 2. Create the Blueprint

Push the repository to GitHub (or GitLab or Bitbucket). In the Render Dashboard choose New >
Blueprint, select the repository, and Render reads `render.yaml`. It prompts once for the values
marked `sync: false`:

| Variable | Value |
|---|---|
| `HVSR_S3_BUCKET` | the bucket name |
| `HVSR_S3_ENDPOINT_URL` | `https://<ACCOUNT_ID>.r2.cloudflarestorage.com` |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | the R2 API token's key pair |
| `HVSR_PUBLIC_BASE_URL` | the site URL, for example `https://hvsr-analyzer.onrender.com` (used in citations) |
| `HVSR_MODERATION_CONTACT` | the public contact for takedown and correction requests |

`HVSR_URL_SIGNING_KEY` is generated by Render. `HVSR_DATABASE_URL` comes from the database.
No secret is written in the repository.

### 3. Issue tokens

Open a Shell on the web service in the Render Dashboard:

```bash
python -m hvsr_web.admin issue-admin-token --name "Operator name"
python -m hvsr_web.admin issue-upload-token --email contributor@example.org
```

Each token is printed once; only its SHA-256 is stored. Give upload tokens to contributors and keep
the administrator token for bank management.

### 4. Check the deployment

From any machine:

```bash
uv run python scripts/smoke.py url https://hvsr-analyzer.onrender.com --blueprint-limits
```

This checks `/healthz`, `/readyz`, the home page, and that `/api/v1/limits` serves the limits
declared in `render.yaml`. It writes nothing.

### 5. First submission

Upload one recording through the web page with an upload token, request the default analysis, and
open the results page. Then download the original recording from the measurement page and compare
its SHA-256 with your file. This is the first end-to-end use of the real bucket.

### Resizing

- More memory per job: raise `HVSR_JOB_MEMORY_BYTES`, `HVSR_MAX_SAMPLES_PER_CHANNEL`, and
  `HVSR_MAX_CANDIDATE_WINDOWS` together with the plan (for example `2c-4g`). Then rerun
  `uv run python scripts/profile_runs.py --blueprint render.yaml --cases large eight_hours --out
  docs/evidence/stage9/performance-render-limits.json --no-markdown`; `tests/stage_09/test_deploy.py`
  checks the new budget.
- More throughput: a separate worker service (`python -m hvsr_web.worker`, same environment) with
  `HVSR_EMBEDDED_WORKER=false` on the web service. Add it only when queues are measured to be too
  long. The largest admitted recording took about 14 s of CPU to upload and analyze on the
  development machine (`docs/performance.md`); Render's CPUs were not measured.
- Database: `0.5c-1g` once the measurement count reaches the thousands (`docs/costs.md`).

## Backups on Render

`python -m hvsr_web.admin backup create DIR` copies every row and every committed object into
`DIR` (`docs/backup-restore.md`). The service's disk is ephemeral and small, so run it from an
operator machine with the service's environment:
1. In the database's access control (IP allow list) settings, temporarily allow the machine's IP
   address.
2. Export the external database URL as `HVSR_DATABASE_URL`, plus the bucket variables.
3. Run `backup create` to a local directory, copy it off-site, and remove the IP address again.

For a large archive, copy the bucket with a provider tool (for example `rclone sync` to a B2
bucket) and keep the backup format for the database and smaller sites. Render's own database
backups are not tested here.

## Docker without Render

```bash
docker build -t hvsr-analyzer --build-arg GIT_COMMIT="$(git rev-parse HEAD)" .
docker run --rm -p 8000:8000 --env-file .env hvsr-analyzer
```

With no environment, the image uses SQLite and a local object store under `/data` (mount a volume
there to keep them). Set `HVSR_EMBEDDED_WORKER=true` for a single container, or run a second
container with the command `python -m hvsr_web.worker`. The server and the worker migrate the
database at startup (`python -m hvsr_web.admin migrate` does it explicitly).
`scripts/smoke.py docker --image hvsr-analyzer` runs the image this way and checks it.

## Local server without Docker

```bash
uv sync
cp .env.example .env    # edit; at least HVSR_URL_SIGNING_KEY and HVSR_EMBEDDED_WORKER=true
set -a; . ./.env; set +a
uv run python -m hvsr_web.admin migrate
uv run uvicorn hvsr_web.api:create_app --factory --port 8000
```

## What was tested

| Check | How | Result |
|---|---|---|
| Blueprint structure | validated offline against Render's published JSON Schema (`tests/stage_09/data/render.schema.json`) | passes; not validated by Render itself (`render blueprints validate` needs the Render CLI and an account) |
| Blueprint values | every `HVSR_*` key is a real setting; the health path returns 200; the pre-deploy command parses | passes |
| Memory budget | measured peaks at the blueprint limits (`docs/evidence/stage9/performance-render-limits.json`) | worst admitted case 664 MiB per job; web plus job budget within 95% of 2 GB |
| Fresh runtime install and startup | `scripts/smoke.py local --clean-install`: runtime-only environment from `uv.lock`, migrate, start, submit, analyze, publish, SIGTERM | passes (AC-S9-11) |
| PostgreSQL | PostgreSQL 16 (pgserver): migrations, concurrent startup, job ceiling and submission races, backup and restore across engines | passes (AC-S9-14) |
| Docker image | `scripts/smoke.py docker`, run by the gate where Docker exists | built and passed in GitHub Actions (runs 39622608537 and 39626471556); skipped on the development machine, which has no Docker |
| CI on GitHub | `.github/workflows/ci.yml` | runs on every push; see `docs/implementation-status.md` for the runs and their results |
| Real bucket (R2, B2, Hetzner) | none | not tested; S3 behavior tested against moto |
| Render deployment | none | not done |
